# Dungeon Generator

This is a dungeon generator that creates dungeons using a cellular automata approach. The generator is written in Python and uses the numpy, matplotlib, and scipy libraries.

The dungeon is intended to be used for the Dungeon game, which is a 2D dungeon crawler game that relies on this script to generate its dungeons. The game is written in GameMaker Studio 2. To run the game, which is currently largely unimplemented, you will need to install GameMaker Studio 2 and import the game files from the `Dungeon` folder.

## Features

### Current

- Procedural dungeon generation with a cellular automata algorithm that creates organic dungeons that are all connected.
- Displays the dungeon with matplotlib.
- Basic title screen for the game.
- Parsing and loading the dungeon into GameMaker.

### Planned

- Correctly generate floor and wall tiles based on dungeon array.
- A player that moves around in the dungeon.
- Interactive objects generated by a LLM that are placed around the room.
- The ability to store multiple dungeons.

## Usage

### Prerequisites

- Python 3
- GameMaker Studio 2 (to run the game; some features may differ between versions, so latest version is recommended)

### Testing Generation

To see the dungeon generation outside of the game, you may first install the required dependencies:

```bash
pip install numpy matplotlib scipy
```

Then, to run the generator and see the dungeon visually:

```python
python generate_dungeon.py
```

The generator will create a dungeon and display it visually using matplotlib. The dungeon will also be exported to a JSON file in the folder `~/Library/Application Support/Dungeon/`.

### Run Game

To run the game, you may open `Dungeon/Dungeon.yyp` in GameMaker Studio and press run. Note that it is large unimplemented.

## Further Development

While the dungeon generation is currently functional, the game is currently largely unimplemented. Future development will focus on implementing the game in GameMaker Studio 2 and smoothing out the connection between the game and any external files and scripts.

The main issue is that the game currently cannot correctly load the dungeons generated by this script. This is due to some quirks with external file handling and object generation in GameMaker Studio 2, which is largely a lightweight indie game development platform that doesn't take external files very nicely.

For reference if any future development of the game should be done, the general structure of the game files is as follows:

- `dungeon_config.py` is a configuration file that sets the size as well as other parameters for the dungeon generator.
- `generate_dungeon.py` generates the dungeon based on the parameters in `dungeon_config.py` and calls `export_dungeon.py`.
- `export_dungeon.py` exports the dungeon as a JSON file to `~/Library/Application Support/Dungeon/`, where it can be accessed by the game.
- `/Dungeon` contains the game files and can be opened with GameMaker Studio 2:
    - This folder is meant to be opened with GameMaker Studio and another editor may not be able to correctly process all the files.
    - The game uses the [xProcess extension](https://samuel-venable.itch.io/gamemaker-extension-collection) to call external scripts
    - On click of the `New Dungeon` button, the `generate_dungeon.gml` script is called, which calls `../generate_dungeon.py`, which in turn generates the dungeon and sends it to `~/Library/Application Support/Dungeon/`. 
    - Then `parse_dungeon.gml` is called, which takes the JSON file, and parses it into a GameMaker 2D array.
    - Finally, `create_dungeon_room.gml` creates a new room and lays down tiles based on the contents of the 2D array. **- note that this feature is where the game starts to be unimplemented. Everything past this point is not implemented yet and is simply provided as a reference for where this project intended to become**
- Then, a player object would be placed in the room, and the player may explore the room.
- In its current form, the room does not have anything to interact with. To add objects dynamically, a large language model (LLM) may be called to generate a JSON of objects to place in the room, such as enemies, doors or gates, traders, or other interactive objects. For example:
```json
{
    {
        "name": "Alice",
        "class": "static",
        "default_message": "Hello, world!",
        "health": 50,
        "damage": 5,
        "inventory": ["sword", "potion"]
    },
    {
        "name": "Bob",
        "class": "trader",
        "default_message": "Hi, how can I help?",
        "health": 20,
        "damage": 5,
        "inventory": ["dagger"]
    },
    {
        "name": "Mallory",
        "class": "enemy",
        "default_message": "Rarr!",
        "health": 100,
        "damage": 20,
        "inventory": ["shield", "club"]
    }
}
```
- This is well within the capabilities of current LLMs.
- This JSON can then be parsed and each character be placed in the room.
- Each dungeon can have an exit gate or similar, so it can be beaten. The advantage of procedurally generating each dungeon is that there are near infinite possible dungeons, so each one is different.

This game at its heart is essentially a dungeon crawler that behaves like Minecraft: each dungeon/world is different, and it is open-ended. The main roadblock is how GameMaker's strange external (and internal) file handling make it difficult for progress to be made without turning off important security features or using workarounds that bloat the codebase and take time to figure out.
